## Introduction

Autonomous vehicles (AVs) must fuse **camera**, **LiDAR**, **radar**, and **HD‑map** data in real time to perceive complex traffic scenes. Transformer‑based backbones have become the de‑facto standard for such **multi‑modal perception** because of their ability to model long‑range dependencies and cross‑modal interactions. However, designing an optimal transformer architecture manually is labor‑intensive and often sub‑optimal for the strict latency budgets of on‑board compute units (e.g., NVIDIA Drive AGX, Qualcomm Snapdragon, custom ASICs).

**Neural Architecture Search (NAS)** offers a systematic way to explore the combinatorial space of possible encoder‑fusion‑decoder designs, automatically discovering architectures that balance **accuracy**, **latency**, and **hardware efficiency**. This tutorial walks through the entire pipeline—from defining a search space tailored for multi‑modal inputs to deploying a latency‑aware transformer on a production vehicle platform.

> **Goal**: By the end of this post you will be able to (1) formulate a NAS problem for multi‑modal transformers, (2) implement a hardware‑aware search loop, and (3) reproduce a real‑world perception stack that meets a sub‑30 ms end‑to‑end latency target on an embedded GPU.

## Fundamentals of Neural Architecture Search (NAS)

### Why NAS?

| Traditional Design | NAS‑Driven Design |
|--------------------|-------------------|
| Hand‑crafted layers, limited to human intuition. | Systematic exploration of millions of candidate topologies. |
| Time‑consuming iteration cycles. | Parallelizable search; can converge within days on a modest cluster. |
| Often over‑parameterized for target hardware. | Directly incorporates **hardware constraints** (e.g., FLOPs, memory, latency). |

NAS has demonstrated state‑of‑the‑art results in image classification, object detection, and speech recognition. Extending it to **multi‑modal transformers** introduces new dimensions: modality‑specific processing, cross‑modal attention patterns, and heterogeneous latency profiles.

### Search Paradigms

| Paradigm | Core Idea | Typical Optimizer |
|----------|-----------|-------------------|
| **Reinforcement Learning (RL)** | Treat architecture generation as a sequential decision process. | Proximal Policy Optimization (PPO) |
| **Evolutionary Algorithms (EA)** | Maintain a population of architectures, apply mutation/crossover. | Regularized Evolution |
| **Differentiable NAS (DARTS‑style)** | Relax discrete choices into continuous weights; train jointly with model parameters. | Gradient descent with bi‑level optimization |
| **One‑Shot / Weight‑Sharing** | Sample many sub‑nets from a super‑net; share weights to reduce training cost. | Random or guided sampling, often combined with RL/EA. |

For latency‑aware multi‑modal transformer search, **weight‑sharing + differentiable latency regularization** (see §6.2) offers the best trade‑off between search efficiency and fidelity.

## Designing a Search Space for Multi‑Modal Inputs

A well‑crafted search space is the cornerstone of successful NAS. Below we outline the key components and provide a **Python‑style configuration** that can be directly fed into a differentiable NAS framework such as **NASBench‑201** or **AutoFormer**.

### Modality‑Specific Encoders

| Choice | Options |
|--------|---------|
| **Tokenization** | Patch embedding, voxel‑pillar, point‑net, sinusoidal positional encoding |
| **Depth** | `{2, 4, 6, 8}` transformer layers per modality |
| **Width** | `{64, 128, 256, 512}` hidden dimensions |
| **Self‑Attention Type** | Standard, **Linformer**, **Performer**, **Sparse‑max** |

### Cross‑Modal Fusion Cells

A *fusion cell* defines how tokens from different streams interact. Typical primitives:

| Primitive | Description |
|-----------|-------------|
| **Concat‑MLP** | Concatenate modality tokens, apply a 2‑layer MLP. |
| **Cross‑Attention** | One modality serves as *query*, others as *key/value*. |
| **Gated Fusion** | Learnable gating per modality (similar to FiLM). |
| **Dynamic Routing** | Capsule‑style routing between modality groups. |

### Token‑Level vs. Feature‑Level Fusion

- **Token‑Level** (early fusion): Merge raw tokens before any deep processing. Pros: maximal interaction; Cons: high memory cost.  
- **Feature‑Level** (late fusion): Fuse after modality‑specific encoders. Pros: reduced compute; Cons: may miss low‑level cues.

Our search space includes a **binary switch** that selects the fusion stage, enabling the optimizer to discover the optimal trade‑off.

### Parameterization Example (Python)

```python
# search_space.py
from nas_lib import Choice, Range, Bool

SEARCH_SPACE = {
    # --- modality encoders -------------------------------------------------
    "camera": {
        "tokenizer": Choice(["patch4x4", "patch8x8"]),
        "depth": Choice([2, 4, 6]),
        "width": Choice([128, 256]),
        "attn_type": Choice(["standard", "linformer"])
    },
    "lidar": {
        "voxel_size": Choice([0.1, 0.2]),
        "depth": Choice([2, 4]),
        "width": Choice([128, 256]),
        "attn_type": Choice(["standard", "performer"])
    },
    # --- fusion cell -------------------------------------------------------
    "fusion": {
        "stage": Choice(["early", "mid", "late"]),   # token vs feature level
        "primitive": Choice(["cross_attn", "concat_mlp", "gated"]),
        "heads": Choice([4, 8]),
        "ffn_ratio": Range(2, 4, step=0.5)           # multiplier for hidden dim
    },
    # --- latency constraints ------------------------------------------------
    "latency_budget_ms": 30.0,
    "hardware": Choice(["nvidia_agx", "snapdragon_8gen3", "custom_asic"])
}
```

The above dictionary can be parsed by most NAS libraries to instantiate a **super‑net** where each choice corresponds to a set of *operation* nodes.

## Latency‑Aware Evaluation Metrics

### Accuracy–Latency Trade‑off

The primary objective is to **maximize perception quality** (e.g., mAP for 3D detection) **subject to a latency ceiling**. A common scalarization:

\[
\mathcal{L} = \underbrace{\mathcal{L}_{\text{task}}}_{\text{Cross‑entropy / detection loss}}
               + \lambda_{\text{lat}} \cdot \max\bigl(0,\; \frac{t_{\text{model}} - t_{\text{budget}}}{t_{\text{budget}}}\bigr)
\]

where \(t_{\text{model}}\) is the predicted latency (see §5.2) and \(\lambda_{\text{lat}}\) balances the penalty.

### Hardware‑Specific Latency Models

| Platform | Modeling Approach |
|----------|-------------------|
| **GPU (CUDA)** | Use **TensorRT** profiling on a representative batch; fit a regression model (e.g., XGBoost) over architectural descriptors. |
| **Edge‑TPU / ASIC** | Build a **lookup table** from micro‑benchmarking each primitive (attention, MLP) at various dimensions. |
| **CPU** | Linear model based on FLOPs + memory bandwidth. |

**Example: TensorRT latency predictor (PyTorch → ONNX → TensorRT)**

```python
import torch
import tensorrt as trt
import numpy as np

def trt_latency(model, input_shape, budget_ms=30, iters=50):
    # Export to ONNX
    dummy = torch.randn(*input_shape).to('cuda')
    torch.onnx.export(model, dummy, "tmp.onnx", opset_version=14)

    # Build TensorRT engine
    TRT_LOGGER = trt.Logger(trt.Logger.WARNING)
    builder = trt.Builder(TRT_LOGGER)
    network = builder.create_network(1 << int(trt.NetworkDefinitionCreationFlag.EXPLICIT_BATCH))
    parser = trt.OnnxParser(network, TRT_LOGGER)
    with open("tmp.onnx", "rb") as f:
        parser.parse(f.read())

    builder.max_batch_size = 1
    builder.max_workspace_size = 1 << 30  # 1 GiB
    engine = builder.build_cuda_engine(network)

    # Warm‑up & timing
    context = engine.create_execution_context()
    d_input = cuda.mem_alloc(dummy.numpy().nbytes)
    d_output = cuda.mem_alloc(dummy.numpy().nbytes)  # placeholder
    cuda.memcpy_htod(d_input, dummy.numpy())
    times = []
    for _ in range(iters):
        start = cuda.Event()
        end = cuda.Event()
        start.record()
        context.execute_v2([int(d_input), int(d_output)])
        end.record()
        end.synchronize()
        times.append(start.time_till(end))
    return np.mean(times)  # ms
```

The function returns an **average latency** that can be directly plugged into the loss term.

### Multi‑Objective Optimization Formulation

When both **energy consumption** and **model size** matter, we treat the problem as a **Pareto optimization**:

\[
